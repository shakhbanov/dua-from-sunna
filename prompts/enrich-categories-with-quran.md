# ПРОМТ: ОБОГАЩЕНИЕ ТЕМАТИЧЕСКИХ КАТЕГОРИЙ КОРАНИЧЕСКИМИ МОЛЬБАМИ

## 0. РОЛЬ И МАНДАТ

Ты работаешь как **редактор-компилятор религиозного справочника** в традиции ахлю-сунна валь-джамаа, соединяющий три дисциплины:

* адаб передачи текста — как у мухаддиса: ничего не передавать без иснада к источнику;
* тематическую систематизацию — как в трудах по абвабам: «Рияд ас-салихин» ан-Навави, «аль-Азкар», «Хисн аль-муслим» аль-Кахтани;
* инженерную дисциплину — как у сопровождающего продакшен-код.

Твоя задача — распределить **109 коранических мольб** по тематическим категориям сайта так, чтобы человек, ищущий «дуа при тревоге» или «дуа за родителей», находил и сунну, и Коран на одной странице.

**Главное правило роли.** Большой имам — это тот, кто **передаёт, а не сочиняет**. Ты не выносишь фетв, не определяешь степень достоверности хадиса своим суждением, не приписываешь мнение мазхабу без ссылки. Всё, что ты утверждаешь, должно быть либо прямо в тексте аята, либо в тафсире с указанием имени муфассира, либо у названного учёного. Формулировка «известно, что» без источника — запрещена.

## 1. ЖЕЛЕЗНЫЕ ПРАВИЛА

Нарушение любого — провал задачи целиком, независимо от качества остального.

**R-01. Арабский текст не набирается заново. Никогда.**
Он уже в `data/quran/*.ts`, сгенерирован из справочного документа скриптом `scripts/build-quran-chapters.mjs`. Ты не добавляешь, не правишь и не «улучшаешь» ни одной харакаты. Если тебе кажется, что в огласовке ошибка — ты пишешь об этом отдельным пунктом в отчёте, а не правишь.

**R-02. Аят не выдумывается и не пересказывается по памяти.**
Каждая мольба уже несёт своё `source: { ru: "Коран, 2:201" }`. Ссылка на суру и аят берётся оттуда, а не из твоей памяти. Если ты хочешь сослаться на аят, которого нет в данных, — ты его не добавляешь, а выносишь в предложения владельцу.

**R-03. Степень достоверности хадиса не присваивается.**
Если в тексте категории упоминается хадис, он должен быть уже в `data/chapters/*.ts` со своей ссылкой. Слова «достоверный», «сахих», «хасан», «слабый» пишутся только если это указано в исходных данных. Своей оценки ты не выносишь.

**R-04. Фикховых предписаний ты не создаёшь.**
Запрещены формулировки вида «читается три раза», «желательно после каждого намаза», «обязательно», «сунна муаккада», если этого нет в исходных данных главы. Разрешено описательное: «эта мольба приведена в суре… в контексте…».

**R-05. Никаких утверждений о награде и последствиях.**
«Кто прочтёт это, тому простятся грехи» — только дословной цитатой с источником. Своими словами — никогда.

**R-06. Тематическая привязка обосновывается текстом мольбы, а не ассоциацией.**
Мольба попадает в категорию «Дуа за родителей», только если её текст обращён о родителях (17:24, 14:41, 71:28). Не «потому что про семью вообще».

**R-07. Спорное — помечается, а не решается.**
Если мольба обоснованно относится к двум категориям — она попадает в обе, это нормально. Если её отнесение спорно по существу (например, требует выбора между тафсирами) — она выносится в раздел «на решение владельца», а не размещается по твоему усмотрению.

**R-08. Ничего не публикуется без проверки человеком.**
Всё, что ты пишешь про религиозное содержание, — черновик со статусом `needs-review`. Ты готовишь изменение, прогоняешь проверки, показываешь диф. Публикует владелец.

**R-09. Существующие тексты категорий не переписываются молча.**
12 категорий уже имеют написанные вручную `summary` и `intro`. Ты их **дополняешь** абзацем о коранической части, а не заменяешь. Каждое изменение существующего текста показывается отдельно и обосновывается.

**R-10. Не ломать то, что работает.**
В репозитории 8 SEO-проверок (`npm run seo:check`). Они должны проходить после твоих изменений. Проверку нельзя ослаблять, исключать файлы или добавлять `continue-on-error`.

## 3. ТЕХНИЧЕСКИЙ БЛОКЕР — УСТРАНИТЬ ПЕРВЫМ

**`src/views/CategoryPage.tsx:39` резолвит главы только по коллекции сунны:**

```ts
const chaptersById = new Map(MOCK_DATABASE.map((c) => [c.id, c]));
const chapters = cat.chapterIds
  .map((id) => chaptersById.get(id))
  .filter((c): c is NonNullable<typeof c> => !!c);   // ← коранические id молча исчезают
```

Если добавить `2003` в `chapterIds`, произойдёт следующее:

1. на странице категории глава **не появится** — `.filter()` её выбросит;
2. на `/kategorii/` счётчик покажет `cat.chapterIds.length`, то есть **соврёт**;
3. сборка не упадёт, проверки не сработают — **тихая потеря контента**.

**Требование:** сначала почини резолв (используй `getChapter(collection, id)` или общий индекс по обеим коллекциям из `data/collections.ts`), затем добавь проверку, которая роняет сборку, если хоть один `chapterId` или `duaId` в `data/categories.ts` не резолвится. Только после этого приступай к контенту.

Проверка — девятая в наборе `scripts/seo-checks.mjs`, в том же стиле, и её обязательно проверить на негативном кейсе: подставь несуществующий id, убедись, что проверка падает, верни как было.

## 4. АРХИТЕКТУРНОЕ РЕШЕНИЕ — ЗАДАЙ ЕГО ВЛАДЕЛЬЦУ ДО НАЧАЛА

`Category.chapterIds: number[]` умеет ссылаться только на **главу целиком**. Для сунны это работает: глава = одна тема. Для Корана — нет: сура «Аль Имран» даёт 14 мольб о стойкости веры, о прощении, о потомстве, о власти и о Судном дне одновременно.

Три варианта, с честной ценой каждого:

**А. Ссылки на уровне мольбы (рекомендуется).**
Добавить в `Category` необязательное поле:

```ts
/** Отдельные мольбы, а не глава целиком. Для Корана, где сура покрывает много тем. */
duaRefs?: Array<{ chapterId: number; duaId: string }>;
```

Страница категории показывает их отдельным блоком «Мольбы из Корана», каждая ссылкой на `/dua-iz-korana/<слаг-суры>/#<duaId>`.
Цена: правка типа, страницы категории и одной проверки. Точность: максимальная.

**Б. Ссылки на главу целиком.**
Дёшево, но категория «Дуа за родителей» затащит все 14 мольб «Аль Имран», из которых к теме относится одна. Это ухудшает страницу и размывает релевантность.

**В. Новые тематические главы поверх сур.**
Возврат к тому, что было снято коммитом `9419908`. Плодит дубли и второй набор URL на тот же текст. Не делать.

Выбор — за владельцем. Не начинай контент, пока он не сделан. При выборе **А** якорь `#<duaId>` должен реально существовать в разметке — проверь, что `DuaPager` или блок мольбы отдаёт `id="2003-13"`, иначе ссылка ведёт в никуда, и это надо добавить.

## 5. ПРИНЦИПЫ ОТБОРА

Для каждой из 109 мольб определи тему **по тексту самой мольбы и по её `title`**, а не по названию суры.

**Опорные соответствия** (проверь каждое по данным, это гипотеза, а не готовый ответ):

| Категория | Коранические темы | Опорные аяты |
|---|---|---|
| `distress` | тревога, беда, болезнь, страх | 21:87 (Юнус), 21:83 (Айюб), 3:173, 9:129 |
| `family` | супруг, потомство, продолжение рода | 25:74, 3:38, 14:40, 37:100 |
| `sickness-death` | болезнь, упокоение с праведными, Судный день | 21:83, 3:193, 7:126 |
| `social` | несправедливость, вражда, отношения | 28:21, 60:5, 26:83 |
| `daily` | пропитание, нужда, вход и выход | 28:24, 23:29, 27:19 |
| `travel` | путь, переселение, безопасность | 17:80, 23:29 |
| `wudu-prayer` | стояние в молитве, принятие дел | 14:40, 3:8 |
| `morning-evening-adhkar` | защита утром и вечером | 113:1–5, 114:1–6 |

**Новые категории — кандидаты.** Часть коранических тем не покрывается ни одной из 12. Предложи создание, обоснуй объёмом (не меньше 4–5 мольб на категорию) и не создавай тонких страниц:

* прощение грехов и покаяние — 7:23, 3:16, 3:147, 23:118 и др.;
* стойкость веры и терпение — 3:8, 2:250, 7:126;
* знание, ясность речи, верное решение — 20:25–28, 20:114, 18:10;
* родители — 17:24, 14:41, 71:28;
* Судный день, свет и спасение — 66:8, 3:191, 3:193, 25:65.

Заметь: это ровно те темы, которые были снятыми тематическими главами до `9419908`. Их URL живут как legacy-заглушки — но **в другом пространстве**: заглушка лежит по `/dua-iz-korana/dua-o-proshchenii-grekhov/`, а категория получила бы `/dua-o-proshchenii-grekhov/`. Коллизии путей не будет, и сторож в `prerender.mjs` промолчит.

Риск здесь другой и тоньше: две почти одинаковые страницы на одну тему — заглушка, канонизирующая на суру, и живая категория. Для человека это дубль, для поиска — размывание релевантности. Поэтому: слаг категории должен отличаться по формулировке от снятого (`dua-o-proshchenii-i-pokayanii` вместо `dua-o-proshchenii-grekhov`), а в тексте категории уместна ссылка на соответствующие суры.

**Порог тонкости.** Категория меньше чем с 4 единицами не создаётся. Лучше положить мольбу в существующую, чем плодить страницу из двух ссылок.

## 6. ЧТО ПИСАТЬ

Для каждой затронутой категории:

**`summary`** — не трогать, если смысл не изменился. Если категория существенно расширилась Кораном, дополнить, не выходя за ~160 символов.

**`intro`** — добавить **один абзац** о коранической части. Требования к нему:

* 40–90 слов;
* называет конкретные мольбы и суры, а не «многие аяты»;
* объясняет, чем коранические мольбы отличаются по положению: это слова, приведённые в Книге Аллаха, а не переданные через хадис — но **без утверждений о превосходстве в награде**, если этого нет в источнике;
* написан на русском и английском, оба варианта равного качества (английский — не подстрочник);
* не повторяет то, что уже сказано в существующих абзацах.

**Тон.** Ровный, справочный, без экзальтации. Читатель пришёл найти мольбу, а не прочитать проповедь. Сравни с уже написанным `intro` категории `morning-evening-adhkar` — держи ту же интонацию.

**Английский.** Транслитерация по общепринятой схеме, единообразно во всём файле: `du'a`, `adhkar`, `Surah al-Baqarah`, `Ayat al-Kursi`. Сверься с тем, как это уже сделано в `data/quran/en.json`.

## 7. ФОРМАТ ИЗМЕНЕНИЙ

* Единственный файл контента — `data/categories.ts`. Данные глав и мольб не трогаются вовсе.
* При варианте **А** — правка типа `Category`, `src/views/CategoryPage.tsx` и одна новая проверка.
* Порядок в `duaRefs` — осмысленный для чтения, не по номеру суры автоматически. Самая известная и общая мольба темы идёт первой.
* Никаких изменений в `data/quran/`, `data/chapters/`, `data/slugs.ts`, `data/quranSlugs.ts`.
* Слаги существующих категорий не меняются. Изменение слага = потеря индексированного URL; если оно всё же нужно, старый URL заводится в `scripts/legacy-urls.json` вместе с преемником.

## 8. ПРОВЕРКА И ПРИЁМКА

Изменение считается готовым только после **всех** пунктов:

```bash
npx tsc --noEmit -p tsconfig.json     # типы
rm -rf dist dist-server && npm run build   # полная сборка с нуля
npm run seo:check                      # 8 + 1 проверок, должны пройти
npx react-doctor --scope changed       # без замечаний
```

И отдельно, руками по готовой сборке:

1. каждый `chapterId` и `duaId` из `data/categories.ts` резолвится — новая проверка это гарантирует;
2. счётчик на `/kategorii/` совпадает с числом реально показанных единиц;
3. якорь `#<duaId>` существует в разметке целевой страницы;
4. ни одна категория не потеряла глав сунны;
5. число живых страниц не изменилось, либо изменилось ровно на число новых категорий × 2 языка, и это объяснено;
6. `sitemap.xml` и сборка совпадают в обе стороны.

**Важно про среду:** GitHub Actions на аккаунте заблокирован по биллингу, деплой ручной. `npm run seo:check` придётся запускать самому — автоматически он не выполнится.
